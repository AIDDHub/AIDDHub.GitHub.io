为什么化学软件仍然适合做成桌面程序

网页应用是科学软件的默认选择，大多数情况下也确实正确：不用安装、所有人同一个版本、部署几乎不花力气。

但有些问题不适合这个形状。对接计算、几十万行的结构表，以及必须跑在受限网络里的流程，是最明显的几个。 这篇写为什么在这些场景里桌面是更合适的答案，以及选择它要付什么代价。

问题的形状

一次对接不是一个 HTTP 请求。它是某台机器上二十分钟的 CPU 计算，要能看着进度、中途改参数， 输出是装了一堆构象的文件夹，而不是一个 JSON 响应。

大化合物表也一样。在浏览器里排序、筛选、聚类二十万行做得到，但结果一旦要和绘图窗口并排放一个小时， 或者喂给一个跑四分钟的模型，浏览器就从优势变成约束。

这类工作流是本地、反复、计算密集的。桌面不是怀旧，是它和问题同形。

本地安装换来了什么

不用上传。 结构、活性表、模型都留在本机。对任何在保密协议下工作的人——也就是手上真有化合物系列的 大多数人——这是前提，不是卖点。

离线可用，内网可用。 工业界和高校的网络里全是代理，什么都要拦。一个签过名的安装包，比一个需要 申请白名单的域名容易批。

没有延迟预算。 打开 50 MB 的 SDF 花多久取决于磁盘，不取决于网络，也不用为了省一次往返去分页。

厂商的服务器挂了，软件还在跑。 三月的版本十一月还能在一台开发者从没见过的机器上打开。

代价

这些取舍是实打实的，应该说清楚。

  • 分发是税。 每个平台的安装包、代码签名、下载托管，以及杀毒软件厂商哪天改主意之后的一场客服对话。
  • 更新要商量。 网页版所有人都在当前版本；桌面版永远有人停在十八个月前的构建上，报告着没人记得的代码。
  • 没有遥测就没有数据。 问题靠邮件发现，这个反馈闭环比任何仪表盘都慢。
  • 远程什么都修不了。 一次热修变成重新打包、重新上传，再写邮件请大家重装。

这些成本，就是大多数新的科学软件选择网页版的原因。

界线在哪里

浏览器是分发渠道，不是计算模型。当一个工具主要是一个表单、一块看板或一个共享数据库时，它属于网页。 当一个工具的核心是视口里的一个分子加 CPU 上的一个求解器时，浏览器就是在原生引擎外面多包了一层， 还要付额外的代价。

由此得到一条简单的规则：原生程序、磁盘上的普通文件、不要账号、不同步。

值得保留的约束

还有一个理由，与技术无关。桌面程序在用户不再需要它的时候就算完成了。没有活跃度指标，没有留存曲线， 也没有动机让工具比问题本身更黏人。

这个约束让设计问题变小：这东西今天能帮人拿到一个站得住脚的结论吗？拿到之后，他可以走开吗？
